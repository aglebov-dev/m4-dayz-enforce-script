# Enforce Tools (DayZ)

[English version / Английская версия](README.md)

VS Code, который наконец понимает **DayZ Enforce Script** — твой мод, его зависимости и
скрипты движка вместе со слоями `modded`. Автокомплит, навигация, поиск ссылок, ошибки до
сборки и проверка настоящим движком по `F5`.

> ⚠️ **Бета.** Между релизами возможны ошибки и изменения — баг-репорты очень приветствуются.

## Проблема

Из коробки VS Code видит EnScript просто текстом. Автокомплит предлагает всех однофамильцев
корпуса, «перейти к определению» уводит в чужой мод, а про опечатку узнаёшь только когда
сервер отказался стартовать — минут через пять и с ошибкой в файле, который ты не трогал.

Плагин вместо этого строит индекс всей картины: твой код, зависимости, скрипты движка
и каждый слой `modded` в порядке загрузки. Всё остальное — следствие.

## Что это даёт

### Автокомплит по настоящему типу

Не «все методы с таким именем», а члены того типа, который реально стоит слева от точки.
Цепочки вызовов, дженерики, `auto`, переменные `foreach`. У каждого пункта видно
класс-владелец и сколько модов уже его трогали.

![Автокомплит с владельцами](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/completion-owners.png)

После имени enum'а предлагаются его значения — с числами и в порядке объявления.

### Навигация, которая учитывает слои

Hover и `F12` резолвят по типу, а не по имени. В попапе — кликабельная сигнатура,
класс-владелец, мод и модуль, все слои `modded` и переопределения в наследниках: сразу
видно, кто ещё менял этот метод. `super` ведёт ровно туда, куда пошёл бы движок.

![Hover с дефинициями и override'ами](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/hover-definitions.png)

### Эксплорер типов

Иконка **M4** в панели слева открывает дерево всего, что плагин знает о проекте, устроенное
как обзорщик проекта: наверху ваш мод (имя — из `build.modName`, иначе имя открытой папки),
внутри **Properties** с манифестом, **Dependencies** со всем, что подгружается (движок и
каждая запись `load[]`), а следом ваши исходники. Изначально всё свёрнуто и разворачивается
лениво, поэтому корпус в 8000 классов открывается мгновенно. Клик по файлу открывает файл,
клик по символу ведёт к определению.

**Под записью дерево повторяет диск, папка в папку.** Проект и так организован — разделы,
моды, скрипт-модули, — и ровно это вы видите. Папка, в которой лежит `config.cpp`,
рисуется модом (свой — синим, зависимость — своим цветом), остальные остаются папками.
Сначала идут папки, потом моды, потом файлы: так мод не теряется среди разделов.

Файлы `config.cpp` тоже в дереве — с классами `CfgPatches` / `CfgMods` и всей их
вложенностью: конфиг это часть мода, а не отдельный мир. Мод, в котором одни ассеты и
конфиг, — просто папка-мод без скриптов, никуда он не прячется.

Дефайны препроцессора — тоже узлы дерева. Файл, в котором нет ничего, кроме `#define` (а
`*_Preload`-аддоны большого мода именно такие), раньше выглядел пустым, и аддон казался одним
`config.cpp`. Теперь дефайны видны прямо там, вместе со значениями.

**Only Scripts** в тулбаре срезает дерево до кода: папки, в которых нигде внутри нет
`.c`/`.cpp`, исчезают, а единственная папка-обёртка, которую кладут внутрь скрипт-модуля по
соглашению Workbench (`5_Mission → DayZExpansion_Core → …`), пропускается — сразу видно
файлы. Пять скрипт-модулей (`1_Core`…`5_Mission`) остаются видимыми даже пустыми: туда
кладут код.

Иконки окрашены так же, как в обзорщике проекта: янтарные папки, свой цвет у вашего кода,
другой — у зависимостей, а каждый вид символа (класс, метод, поле, константа, enum, дефайн)
в том цвете, которым его уже красит ВАША тема в Outline и хлебных крошках.

![Эксплорер рядом с попапом класса](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/explorer-symbols-popup.png)

Файла проекта ещё нет? Панель так и говорит и предлагает его создать — как VS Code предлагает
`launch.json`. В созданном `enforce.project.json` уже проставлены имя мода (по имени папки) и
папка сборки, а если скрипты движка удалось найти — то и они.

Скрипты движка обычно так и лежат запакованными в игре (`dta/scripts.pbo`), поэтому, когда их
не нашли, в дереве появляется строка **engine — not set** с кнопкой: укажите любую папку со
стандартной структурой `1_Core / 2_GameLib / 3_Game / 4_World / 5_Mission`. Что там внутри —
ваше дело, проверяется только структура.

Рядом с манифестом плагин ведёт `enforce.deps.json` — что именно подключено. Мод не обязан
быть из воркшопа, а рядом на диске легко лежит вторая копия того же мода: свежее или старее,
снаружи не отличить. Путь на вопрос «тот ли это файл» не отвечает, поэтому в локе — **хеш
каждого pbo** и папка распаковки, которую реально читает индекс (плюс версия автора из
`CfgMods`, если он её указал). Обновляется сам при каждом перестроении индекса — после
правки конфига руками или кнопок ниже, — а посмотреть можно в **Properties**.

**Эксплорер — просмотрщик, а не файловый менеджер.** По правой кнопке ровно то, что нужно
просмотрщику: копировать путь, копировать относительный путь, открыть расположение.
Создавать, переименовывать и удалять — это к встроенному проводнику, у него это выходит
лучше. Пока строится индекс, панель заблокирована — жать ещё нечего.

Зависимости подключаются прямо из дерева: **+** на ветке `Dependencies` открывает выбор папки
мода или `.pbo` и дописывает его в манифест (имя — из имени папки или файла), **−** на записи
убирает её, спросив подтверждение. Уходит только запись манифеста — на диске ничего не
трогаем, и комментарии, которыми вы размечали `enforce.project.json`, переживают правку.

У скриптов своя зелёная иконка **C**, а всё, что открывается только для чтения (движок и
любая зависимость), помечено замком СРАЗУ, а не когда файл уже открыт. Панель открывается с
раскрытым вашим модом, зависимости остаются свёрнутыми, пока не понадобятся.

Дерево не скачет само: оно меняется только от вашего клика или по значку **☰** из попапа.

В тулбаре слева направо: поиск по подстроке среди типов и членов, фильтры (методы / свойства /
константы / глобалы / дефайны), обновление (сначала перепроверяет индекс), переход к
редактируемому файлу (к любому подключённому сурсу — своему или из зависимости), «свернуть
всё», «развернуть проект» и **Only Scripts**. Разворачивается только ваш мод и только ДО
файлов — не внутрь них и никогда внутрь зависимостей: это значило бы обойти тысячи классов
ради одного клика.
«Свернуть всё» оставляет корень проекта раскрытым, чтобы панель не схлопывалась в одну строку. У каждого определения в попапе
есть значок **☰** — открывает эксплорер и выделяет ровно это определение; удобно, когда у
типа несколько `modded`-слоёв и надо увидеть, где какой лежит.

### Дефайны: видно, что включено, что нет и что не соберётся

Половина DayZ-проекта живёт под `#ifdef`. Плагин собирает дефайны отовсюду, откуда они
вообще берутся — `#define` в скриптах, `defines[]` в `config.cpp`, имена модов и ручки,
которые автор оставил закомментированными, — и показывает результат:

- мёртвые блоки `#ifdef` затемняются, и ты не читаешь код, которого нет;
- hover на гарде говорит, включён он или нет и откуда это значение;
- `F12` ведёт к объявлению, `Shift+F12` показывает все места, где гард используется;
- гард, который нигде не объявлен, подсвечивается как ошибка — такой код не соберётся никогда.

![Карточка необъявленного дефайна и панель ссылок под ней](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/define-unknown.png)

![Карточка дефайна, объявление которого закомментировано](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/define-off.png)

С типами то же самое: если все объявления класса лежат под выключенной ручкой, его
использования затемняются и помечаются. Это движковый `Unknown type` — показанный в
редакторе, а не в конце сборки, и с указанием виноватой ручки.

### Ошибки ловятся до сборки

На сохранении файл парсится, проверяется линтером и семантикой: необъявленные методы и
функции, неизвестные типы, неверное число аргументов и переменные, которых никто не
объявлял — в том числе те, что передают out-параметром, как `Class.CastTo(ai, …)` с опечаткой
в `ai`. Серьёзность подогнана под движок: что он прощает — предупреждение, что отвергает —
ошибка. Перенос строки, разрывающий выражение, — тоже ошибка: движок компилирует построчно и
разрешает заканчивать строку только на `(`, `,` или `=`.

Необъявленные имена ищем только в ВАШЕМ коде: часть своих констант движок объявляет со стороны
C++, и судить по нашим данным чужие read-only исходники значило бы врать. Для таких имён есть
секция `environments` — пишете их со значениями, и они входят в индекс наравне с остальным:

```jsonc
"environments": { "DBT_OK": 0, "DBB_NONE": 0, "DMT_INFO": 1 }
```

По ним работают поиск, hover и переход к объявлению — переход приводит на ту самую строку
вашего манифеста.

![Диагностика](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/diagnostics.png)

По желанию та же проверка прогоняется по всему проекту прямо перед сборкой — чтобы не
тратить пятиминутный круг через сервер на опечатку. Останавливает только на том, что движок
не примет, и в диалоге всегда есть **Build anyway**.

Предполёт — это **отдельный проход по всему проекту**, а не живой анализ: его находки помечены
`[pre-flight]` и остаются в Problems до следующего запуска. Правка файла снимает его пометки
по этому файлу; правка `enforce.project.json` — нет: изменение `defines` или `environments`
способно перевернуть вердикт по каждому файлу, поэтому список честен только сразу после
прогона. Поправили что-то через манифест — перезапустите сборку (F5), чтобы список обновился.
Живой анализ в редакторе обновляется на сохранении и от предполёта не зависит.

![Предполёт остановил сборку и предложил перейти к первой ошибке](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/preflight-dialog.png)

### Одна клавиша — собрать и спросить движок

`F5` пакует мод в PBO (без AddonBuilder и прочих тулов) и гоняет компиляцию headless
DayZ Server — вердикт настоящего компилятора секунд за десять. Первопричины отделены от
каскада, который за ними тянется, и каждая ошибка замаплена обратно на твой файл в панели
Problems. `Ctrl+Shift+B` — только собрать PBO.

Упаковщик кладёт в PBO **только скрипты** — этого достаточно, чтобы движок скомпилировал
код и вынес вердикт. Полноценная упаковка мода, с ассетами, появится позже.

![Проверка движком](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/build-check.png)

Лог сборки раскрашен, а каждый путь в нём кликабельный — включая `config.cpp` пропущенного
модуля, по которому видно, почему его пропустили. Повторный `F5` после неудачи просто
работает: плагин дожидается, пока предыдущий сервер закроется.

## Как начать

### 1. Распакованные скрипты игры

Плагин читает ванильные скрипты как обычные исходники, поэтому они нужны на диске
распакованными. Обычный путь — **DayZ Tools** → *Extract Game Data*: он монтирует Work Drive
как `P:` и раскладывает скрипты в `P:\scripts` (папки `1_Core` … `5_Mission`). Подойдёт и
любая другая локальная копия — просто укажи в конфиге, где она лежит.

С модами-зависимостями проще: в `load[]` можно указать **исходники**, распакованный аддон —
или просто воркшоп-папку **`@Mod` с запакованными `.pbo`**. Запакованные моды распаковываются
автоматически (только скрипты и конфиги; бинаризованные конфиги разворачиваются обратно в
текст) в кэш плагина и перераспаковываются при обновлении мода.

⚠️ **Прежде чем указывать в `load[]` чужой мод, прочтите предупреждение в начале страницы —
ответственность за распаковку чужой работы целиком на вас.**

**Обфусцированные моды** открываются в режиме *API-only*: плагин достаёт объявления —
заголовки классов, сигнатуры методов, типы полей, enum'ы — и **не трогает тела**. Автокомплит,
навигация и проверка типов по такому моду работают, а реализация остаётся там, где её оставил
автор. **Результат при этом не гарантируется:** по тем или иным причинам API может извлечься
частично или не извлечься вовсе.

### 2. `enforce.project.json` в корне проекта

Файл кладётся рядом с `config.cpp` твоего мода. Минимальный работает буквально такой:

```jsonc
{}
```

Но лучше сразу начать с такого — ванильные скрипты, имя мода, куда собирать и где стоит
DayZ Server для отладки:

```jsonc
{
  "engine": "P:/scripts",
  "build": {
    "modName": "@MyMod",
    "outDir": "./builds",
    "serverExe": "D:/Steam/steamapps/common/DayZServer/DayZServer_x64.exe",
    "serverCwd": "D:/Steam/steamapps/common/DayZServer"
  }
}
```

Зависимости добавишь, когда понадобятся, — ключ `load[]`, см. справочник ниже. Ключи в
манифесте подсказываются прямо при наборе, а опечатка подчёркивается сразу, а не молча
перестаёт работать.

![Автокомплит ключей в enforce.project.json](https://raw.githubusercontent.com/aglebov-dev/m4-dayz-enforce-script/main/images/manifest-completion.png)

### 3. Запуск по `F5`

Создай `.vscode/launch.json` в корне воркспейса:

```jsonc
{
  "version": "0.2.0",
  "configurations": [
    { "type": "enforce", "request": "launch", "name": "Enforce: Build & Check" }
  ]
}
```

VS Code предложит её и сам: *Run and Debug* → *create a launch.json file* →
**Enforce Build & Check**. Больше ничего не требуется — по `F5` плагин соберёт PBO и
прогонит проверку движком.

### Нет DayZ Server под рукой?

Тогда проверяй код нашим анализатором — включи `preflight`:

```jsonc
{
  "engine": "P:/scripts",
  "build": { "preflight": true }
}
```

По `F5` плагин сначала прогонит проверку по всему проекту и покажет ошибки, а потом упрётся
в отсутствующий сервер и честно об этом скажет. Ни запакованные зависимости (`build.deps`),
ни путь к серверу для такой проверки не нужны — а вот исходники зависимостей в `load[]`
указать стоит, иначе резолв будет неполным. Так дольше: проверка не такая полная, как
вердикт настоящего компилятора, и часть ошибок вскроется позже, уже на сервере. Зато
начать можно без игры.

## Команды

| Команда | Описание |
| --- | --- |
| `Enforce: Find All References (Panel)` | Панель references для символа под курсором (`Shift+F12`) |
| `Enforce: Build Check (Engine Compile)` | PBO + headless-компиляция движком (`F5`) |
| `Enforce: Rebuild Index` | Принудительная полная переиндексация |
| `Enforce: Show All Modifications (discovery)` | Все modded-слои класса |
| `Enforce: Declare Unknown Defines in enforce.project.json` | Дописать все неизвестные дефайны в манифест как `false` |

## Настройки

| Настройка | Дефолт | Описание |
| --- | --- | --- |
| `enforce.workDrive` | `P:` | Work Drive с распакованными скриптами движка |
| `enforce.parseDiagnostics` | `warning` | Диагностика парсинга: warning / error / off |
| `enforce.semanticDiagnostics` | `warning` | Семантическая диагностика: warning / error / off |
| `enforce.unknownDefines` | `warning` | Гарды, дефайн которых нигде не объявлен |
| `enforce.deadTypeDiagnostics` | `warning` | Типы, объявленные только под выключенной ручкой |
| `enforce.dimDeadTypes` | `true` | Затемнять такие типы в редакторе |
| `enforce.conditionalMembers` | `hide` | Члены за ложным гардом: hide / dim |
| `enforce.codeLensReferences` | `true` | «N references» над декларациями |
| `enforce.inlayHints.autoTypes` | `true` | Показывать выведенный тип для `auto` |
| `enforce.references.includeTextMatches` | `false` | Показывать текстовые совпадения в панели по умолчанию |
| `enforce.preflight` | `false` | Проверять проект перед запуском сборки |
| `enforce.readonlyExternal` | `true` | Открывать исходники движка и зависимостей read-only |
| `enforce.autoRefreshSeconds` | `300` | Подхватывать изменения вне воркспейса (0 = выкл) |
| `enforce.formatting` | `{}` | Опции форматтера (отступы, скобки, путь к AStyle) |
| `enforce.build` | — | Дефолты сборки, перекрываются `build{}` в манифесте |

## Справочник `enforce.project.json`

Все ключи необязательные. Максимально заполненный пример:

```jsonc
{
  // ===== ЧТО ИНДЕКСИРУЕТСЯ ==================================================
  // Отсюда плагин узнаёт, какой код он читает: от этого зависят автокомплит,
  // переходы, ссылки и диагностика.

  // Распакованные скрипты базовой игры (папка с 1_Core … 5_Mission).
  // Убери ключ — возьмётся <workDrive>/scripts.
  "engine": "E:/DayZ/WorkDrive/scripts",

  // Моды-зависимости, в порядке загрузки: исходники, распакованный аддон или
  // ЗАПАКОВАННЫЙ мод — папка @Mod с addons/*.pbo (или одиночный .pbo). Запакованные
  // распаковываются в кэш плагина автоматически; обфусцированные дают API-only вид
  // (объявления без тел). Папка с несколькими модами (как DayZ-Expansion-Scripts)
  // разворачивается в слои автоматически.
  "load": [
    // github.com/Arkensor/DayZ-CommunityFramework
    { "name": "CF",        "path": "D:/mods/DayZ-CommunityFramework/JM/CF" },
    // github.com/salutesh/DayZ-Expansion-Scripts
    { "name": "Expansion", "path": "D:/mods/DayZ-Expansion-Scripts" },
    // запакованный воркшоп-мод — распакуется сам
    { "name": "COT",       "path": "D:/Steam/steamapps/common/DayZ/!Workshop/@Community-Online-Tools" }
  ],

  // Твой собственный код. Не нужен, если исходники лежат рядом с манифестом.
  "project": [
    { "name": "MyMod", "path": "./src" }
  ],

  // ===== ЧТО СЧИТАТЬ ВКЛЮЧЁННЫМ =============================================
  // Управляет #ifdef: что затемняется, какие члены видны в автокомплите,
  // какие типы помечены как несобираемые.

  // Дефайны, которых не видно из исходников: те, что движок добавляет сам, и те,
  // что приходят из закрытых PBO. Всё объявленное в твоём коде и зависимостях
  // подхватывается автоматически — значение отсюда просто важнее.
  // Проверка движком печатает его реальный список и предлагает импортировать.
  "defines": {
    "PLATFORM_WINDOWS": true,
    "SERVER": true,
    "DZ_Expansion_Core": true,
    "DIAG": false
  },

  // ===== ПОИСК ССЫЛОК =======================================================
  // Насколько широко ищем использования и что показываем в панели.

  // Разрешить ссылкам, CodeLens и Shift+F12 работать и на файлах движка и
  // зависимостей. У популярных типов движка бывают тысячи использований.
  "externalReferences": true,

  "references": {
    // Показывать текстовые совпадения в панели по умолчанию (кнопка в панели есть всегда).
    "includeTextMatches": false
  },

  // ===== СБОРКА И ПРОВЕРКА ДВИЖКОМ (F5) =====================================
  // Всё, что нужно, чтобы упаковать мод в PBO и скормить его headless-серверу.
  // Если проверка движком не нужна, хватит одного preflight.

  "build": {
    // Проверить проект нашим анализатором перед запуском движка.
    "preflight": true,

    "modName": "@MyMod",            // имя выходной папки
    "outDir": "./builds",           // артефакты: <outDir>/<modName>/addons/*.pbo

    // Запакованные моды-зависимости для -mod=, в порядке загрузки.
    "deps": [
      "D:/Steam/steamapps/common/DayZ/!Workshop/@CF",
      "D:/Steam/steamapps/common/DayZ/!Workshop/@DayZ-Expansion-Core"
    ],

    // Где лежит DayZ Server. Убери оба ключа — найдётся автоматически по Steam.
    // Нужен DayZServer_x64.exe; DayZDiag требует запущенный клиент Steam.
    "serverExe": "E:/Games/SteamLibrary/steamapps/common/DayZServer/DayZServer_x64.exe",
    "serverCwd": "E:/Games/SteamLibrary/steamapps/common/DayZServer",

    "mission": "mpmissions/dayzOffline.chernarusplus",
    "timeoutSec": 240
  }
}
```

В путях работают и `/`, и `\\`. Префикс PBO не настраивается — он берётся из `config.cpp`
каждого модуля, а проект из нескольких модулей пакуется в отдельный PBO на каждый модуль.
